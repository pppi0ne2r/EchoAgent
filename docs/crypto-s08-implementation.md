# S08：计算预算、超时与进程清理

状态：2026-10-21 已核实通过（定向测试与真实 Docker 可控任务）。仅修改本地，未提交或推送远端；未运行真实模型解题。

## 已实现

- 密码 worker 默认预算为 `wall_seconds=300`、`memory_mb=1024`、`output_bytes=4194304`，硬上限分别为 1800 秒、2048 MiB、8388608 字节。项目 `default_budget` 与 intent `budget` 可在上限内覆盖；无效或未支持的字段在规划时被拒绝。普通 Web 项目继续使用原有超时和并发配置。
- 密码计算有独立于模型槽位的 1 个计算槽；同一批 explore 也只并行 1 个密码 intent。密码 worker 关闭“无 stdout/stderr 就超时”的判定，但始终保留硬墙钟截止。stdout/stderr 的累计字节数受限；读流按 4096 字符分片，避免单个无换行长输出绕过上限。密码容器创建时设置内存、swap、PID 数和 CPU 速率限制；每次 worker 执行前用 `docker update` 应用该 intent 的内存额度，兼容此前创建的容器。
- 每次密码 worker 结束，无论完成、超时、输出/内存耗尽还是异常，都重启项目容器以清理 `docker exec` 留下的派生进程；用户主动停止时则强制停止容器。S04 的输入和 intent 产物挂载仍保留。执行记录包含 `compute_id`、有效预算、`exit_reason`、计划范围和实际覆盖范围。`timeout`、`budget_exhausted`、`solver_unknown`、`tool_error`、`cancelled` 与 `range_exhausted` 分开记录。
- 超时或预算耗尽时，已经输出且可解析的观察仍进入原有部分事实保存链路；当前计算保持错误/未证明状态，不生成全局“无解”结论。检查点引用在生产调度客户端经真实文件的大小和 SHA-256 核验，续算前再次核验；错误引用从执行记录中移除并留下原因，不能用于 S07 续算。HTTP 调度客户端使用只读的 `/projects/{id}/artifacts/verify` 接口核验。
- S07 的“增加预算可重试”现在比较实际生效预算，显式写出与默认值相同的数字不算提高预算。同范围最多 3 次尝试；扩大失败区间但没有新预算/检查点时，只执行旧计划外的新片段，不把旧区间误判为已穷尽。reason 连续 3 次只规划被去重的相同计算时沿用原有无进展停止行为。

## 核实

`tests.test_crypto_s08` 的 9 项定向测试涵盖预算边界、静默但正常完成、硬墙钟/输出限制、部分事实、单计算槽、无效检查点、续算前重验、真实字节核验 API，以及重复规划停止。`tests.crypto_s08_docker_smoke` 使用现有本地 `echo-agent-worker:crypto-s03` 镜像创建一个随机命名临时容器，实际运行可控 Python 子进程：

- 静默任务到墙钟截止后保存此前 JSON，绑定挂载的检查点字节在容器重启后仍可从宿主机读取；容器内派生进程消失，容器可继续运行。`docker inspect` 显示 intent 的 512 MiB 内存硬限额。
- 超输出任务触发 `budget_exhausted`，派生进程消失；256 MiB 容器内执行 400 MiB 分配也触发 `budget_exhausted`，实际 `HostConfig.Memory` 为 256 MiB。
- 用户停止正在执行的任务后，容器变为 `exited`，运行线程结束。测试末尾移除该临时容器。

相关 S04–S07 和原 Web 调度回归另行运行；未运行旧测试全集，也未接触现有任务数据库。

## 边界

本阶段限制的是密码 worker 的运行与 Docker 容器资源，不改变普通 Web 容器。实际模型规划仍可能给出不合理的算法或参数；预算能阻止无界运行，不能保证求解正确。内存和 PID 限额针对整个密码项目容器，多个独立项目各有自己的容器；不是跨项目的全机总配额。S09 仍需独立验证候选答案并决定完成门槛。
