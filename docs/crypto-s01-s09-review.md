## 1. 总体判断

**保留 fact/intent 图、增加密码任务分支的方向合理，但目前还不能认定第一版密码学能力已经可靠闭环。** S01–S09 已有阶段性交付和历史验证记录；其中“固定样例通过”不能扩大为“所有入口、题型和完成条件均已通过”。S10 可以用于暴露问题，但应先处理下述阻塞项，再做最终验收。

当前主要不足集中在三个层面：

1. **执行链路没有完全贯通。** 网页后台客户端缺少候选验证方法，已有测试替身具备该方法，因此没有暴露真实入口的遗漏。
2. **证据规则还不完整。** 验算某个候选成立，与完成题目要求之间缺少明确契约；省略模型输出字段也可能改变候选的信任等级。
3. **支持范围与计划不匹配。** 第一版计划包括多输入、编码、异或和约束求解，最终验证器却只接受两类严格输入格式；依赖跨步骤保留同一连接或旧会话数据的交互流程，也不能直接套用当前清理策略。继承方法并在新连接内重放的流程不因此受阻。

不建议为此重写图引擎，也不建议先增加 SageMath 等大型依赖。优先补齐目标、证据、入口和运行生命周期，才符合低配置、稳定的目标。

本文分级：**P1** 为会阻断既定流程或导致完成语义错误的优先问题；**P2** 为适用边界、稳定性或维护问题。静态确认表示代码路径可直接确定；运行风险表示触发概率和实际表现仍需后续验证。除 R05 明确记录的后续提示词调整外，以下整改均为建议，尚未实施。

## 2. 发现与影响

### R01 · P1：网页后台没有接入候选验证，两个客户端语义不一致

**证据：静态确认。** [dispatcher_runner.py](../echo_agent/server/dispatcher_runner.py) 第 144 行用 `StoreDispatcherClient` 创建后台调度器；该类第 250 行起仅有 `verify_crypto_artifact`，没有 `verify_crypto_candidate`。[core.py](../echo_agent/dispatcher/core.py) 第 1330 行起执行 `verify.candidate` 时直接调用后者；第 1297 行起完成检查发现方法不存在则返回 `False`。HTTP [client.py](../echo_agent/dispatcher/client.py) 和 [app.py](../echo_agent/server/app.py) 已有该方法及接口。

**影响：** 网页启动的密码任务进入验证 intent 会调用不存在的方法，完成检查也无法放行。HTTP 路径样例通过不能证明此路径通过。后台 `save_project` 还缺少 HTTP PUT 所做的输入清单不可变检查和输入文件哈希复核，说明差异不只一个方法。

**建议：** 将验证与必要的保存约束放入可共用的服务逻辑，让两个客户端调用同一实现；不再分别复制规则。只对 `crypto` 执行密码规则。

**后续验收：** 同一候选分别通过真实 HTTP 客户端和真实 `StoreDispatcherClient` 完成“保存 → 验证 → reason → 完成”；输入发生变化时，两条路径拒绝行为一致。不得只用自行补齐方法的假客户端替代后台入口。

### R02 · P1：数学条件成立不等于完成目标，多解策略缺失

**证据：静态确认。** [crypto_verify.py](../echo_agent/crypto_verify.py) 第 84–141 行由候选提供 `answer_kind`，可选择明文、因子或私钥指数；验证器没有检查项目 objective 要求哪一种。明文分支只在 `unique_root is None` 时返回 `inconclusive`，`unique_root=False` 仍会返回 `pass`。[core.py](../echo_agent/dispatcher/core.py) 的完成门槛比较新旧 `pass` 记录，并不继续判断目标类型或唯一性要求。

**影响：** 题目要求恢复明文时，正确的因子答案也能得到可供完成门槛使用的 `pass`；题目要求唯一明文时，一个可行根也可能被当成最终答案。保留候选集合本身并没有解决完成判定。

**静态推演例子（本轮未执行）：** `n=15,e=2,c=4` 有 `2、7、8、13` 四个根。当前逻辑接受其中一个并记录“不唯一”，而完成层只要求当前仍为 `pass`。如果目标是“找任一根”，这样可以成立；如果目标是“恢复唯一明文”，证据不足。[test_crypto_s09.py](../tests/test_crypto_s09.py) 的多根样例明确期待 `pass`，但未覆盖这两类目标的不同完成结果。

**建议：** 补充受控的目标与验证约定，至少区分所求对象、答案表示、任一解/唯一解/完整解集和适用约束。由项目任务定义确定，不能由求解 worker 自行选择更容易的目标。将“候选满足关系”和“满足项目完成条件”分别记录；验证还需绑定目标版本，目标变更后旧结论不能直接复用。

**后续验收：** 明文任务拒绝仅因子结果；任一解与唯一解任务对相同多根输入有不同结论；题目目标修改后重新判定；有真实消歧条件时允许对应候选完成。大整数素性检查目前使用 probable-prime 规则，报告不能把它写成所有规模下的严格素性证明。

### R03 · P1：规划可处理的题型比最终验证可接受的题型宽得多

**证据：静态确认与设计边界。** [crypto_verify.py](../echo_agent/crypto_verify.py) 的 `verify_candidate` 要求恰好一个 `source_input_id`，仅分派 RSA/AES。RSA 输入要求唯一的 ASCII `n=、e=、c=` 行，最终明文答案要求十进制 `str(m)`；AES 要求特定 JSON 清单、GCM/CBC 模式，以及原始输入中的 `known_plaintext_sha256`。

**影响：**

- 多模数文件、源码加密文、PEM、原始二进制等输入，虽然可以上传和交给 worker，不能直接进入当前完成验证。
- RSA 的整数到字节、前导零、字节序、填充和最终 flag 表示没有形成完整验证链。算出整数不等于交付题目所需的文本答案。
- 编码、异或、随机数、Z3 约束题没有对应最终验证分支；不能把工具已安装等同于题型已支持。
- 很多正常 AES 题没有给出明文哈希。即使满足题目提供的认证或其他约束，也会被当前统一前置要求挡住。此处应描述为“验证器不支持/证据不足”，不能描述为数学解不存在。

**建议：** 先确定第一版实际支持矩阵，再给每种题型定义小型确定性验证器。增加来源可追溯的参数提取步骤，记录输入文件、位置、解析规则和派生关系；不能把 worker 自行生成的参数清单或明文哈希当成题目原始证据。支持多输入绑定，并明确 RSA 字节转换契约。AES 按模式、密钥来源和目标使用不同标准：GCM 的认证结果、题目约束等应按适用条件判断；CBC 重加密、可打印或 flag 外形单独都不能证明答案正确。

**后续验收：** 至少覆盖源码与密文分离、多输入共享因子 RSA、含前导零的输出、未提供明文哈希但具有可核实约束的样例，以及明确不支持的题型。通用约束校验必须受限执行；不能通过运行求解者任意脚本并信任其退出码来替代独立验证。

### R04 · P1：候选与 evidence 的隔离依赖模型主动填写字段

**证据：静态确认。** [core.py](../echo_agent/dispatcher/core.py) 第 983 行起，仅在密码项目且 `result.crypto` 非空时走专用结果处理；省略该对象会落入通用 evidence 保存路径。专用处理和 `_add_prior_fact` 也只对显式 `claim_status=candidate/hypothesis` 做分离，其余有效观察文本可能直接成为 evidence。第 1266 行起 `_save_crypto_candidate` 在缺少答案或出现 `ValueError` 时静默返回，但调用处仍可能标记 intent 完成并写下 `candidate saved`。

**影响：** 模型少填字段就可能把候选提升为规划依据，或者丢失候选却留下“已经保存”的记录。最终验证门槛仍能阻止仅凭该 evidence 直接完成，但前面的推理、去重和续算已可能受到错误信任等级影响。省略 `crypto` 还会缺少对应专用执行记录；这不等于执行器硬预算失效。

**建议：** 对 `task_type=crypto` 固定使用密码结果入口，不让可选字段决定信任等级。缺失/不合规输出先保存为待验证观察或候选并给出诊断；候选保存返回明确结果，失败不得声称成功。区分原始观察、派生断言、候选与独立验算结论，不要求每条普通观察都重跑昂贵验证。

**后续验收：** 对省略 `crypto`、省略 `claim_status`、缺少 candidate.answer、部分输出和超时保留结果分别检查；没有足够元数据的候选不能自动升级为已证实事实，失败信息不能丢失。

### R05 · P2（需保留不可重放状态时优先处理）：跨连接误用会话数据的风险

**证据：静态确认。** [agents.py](../echo_agent/dispatcher/agents.py) 第 168 行起在密码 worker 结束的 `finally` 中重置容器；第 703 行的实现是 `docker restart -t 0`。它不只在超时发生，正常 intent 完成也会执行。初次复审时 [container/AGENTS.md](../container/AGENTS.md) 的通用 tmux 建议与密码分支存在冲突，密码提示也仅定位为离线题；同日后续已按下述约定补充提示词。

**影响与收窄：** 重启使本地 TCP 连接、tmux 和进程内状态消失，不代表远端靶机被重启或以后不能连接。远端是否换密钥由服务实现决定。若交付的是方法和脚本，下个 intent 可以重新读取参数并完整重放，即使密钥变化也不构成缺陷。风险限于复用旧会话样本/参数、累积查询、一次性机会或无法按预算重放的场景；旧 fact 仍是历史观察，但不能自动变成当前连接的有效参数。最初把所有 nc 题视为会话阻塞的表述过宽，按用户明确的设计意图予以修正。

**采用的最小方案：** 跨 intent 交付方法、已核实前提、持久脚本和来源记录；新连接重新读取参数并核实前提，把依赖同一连接的操作放在一个有时间与请求次数边界的 intent 内。离线和已核实稳定的数据仍可复用。无法重放的会话状态如实报告；仅在确有需求时再引入会话管理，不因该项直接取消容器清理。方法泛化尚未验证时仍是待验证假设，不能借“继承思路”绕过 fact 的证据要求。

**同日后续提示词调整：** first_run、explore、reason 共用 8 条跨 intent 继承规则，分别补充低成本识别、脚本去硬编码检查、有界重放规划；worker 的 `AGENTS.md` 增加仅对 `task_type=crypto` 生效的规则。未新增数据结构字段，未改变容器生命周期、验证器或去重逻辑。已做离线提示词生成检查：三个密码模式均含完整规则，固定 general 项目的三个提示词 SHA-256 与修改前一致。此检查不证明真实模型一定遵从，也没有实现运行时会话绑定与自动失效。

**后续验收：** 使用受控服务检查方法能在新密钥下重新执行、旧样本不混用、前提不成立时停止，以及请求额度、超时和取消。提示词不能扩大 R03 的最终验证器支持范围，不能用离线提示词检查声称 nc 题已端到端支持。复审和本次提示词调整均未连接此前提供的题目地址，也未参与求解。

### R06 · P2：预算主要约束求解 worker，验证链路仍有独立风险

**证据：代码配置已确认，实际超时/残留行为未实测。** [client.py](../echo_agent/dispatcher/client.py) 第 206 行 HTTP 超时为 10 秒；[crypto_verify.py](../echo_agent/crypto_verify.py) 第 220 行起 Docker AES 校验允许运行 30 秒，清理另有超时。可重试的网络错误会触发 HTTP 重试；服务端计算并不因此自动取消。该临时验证容器使用独立 `subprocess.run`，没有接入 worker 的进程登记与停止管理。

此外，RSA 与可用的本机 AES 库直接在服务端进程内计算。1 MiB 输入上限在 `verify_ref` 完整读取并计算哈希之后才检查；相关产物也会全量哈希。[crypto_files.py](../echo_agent/crypto_files.py) 第 68 行没有累计读取预算。因此已有长度和位数限制只能降低工作量，不能代表整个验证链路受 S08 硬预算覆盖。

**影响：** 慢启动时客户端可能先超时、服务端继续运行；部分错误路径重试会重复计算。停止项目不一定及时终止独立验证容器。多项目和直接 API 请求的总资源也不受单个 dispatcher 的密码工作槽统一限制。上述都是运行风险，不能写成已经发生的事故。

**建议：** 为验证设置一致的请求期限、计算期限、可取消执行和并发上限；避免仅提高超时而不处理重复请求。文件校验在读取前和读取中检查大小/累计预算。统一记录验证后端、耗时、终止原因和清理结果。保留当前 Docker 限额，并为宿主机执行路径定义对应边界。

**后续验收：** 超过 10 秒但未超验证预算的受控校验、停止期间的校验、多项目请求和大产物哈希；确认状态、取消和资源占用符合约定。

### R07 · P2：去重仍部分依赖自然语言，依赖版本绑定不完整

**证据：静态确认。** [crypto_dedup.py](../echo_agent/crypto_dedup.py) 第 53 行起将前提的 `description/typed_value/source_input_ids/claim_status` 放入摘要，没有包含候选内容、产物引用或递归依赖值；方法仅做去空格与大小写规范化。第 99 行起同范围重试主要要求新检查点或增加预算。

**影响：** 相同语义仅改写描述可能成为新动作；同描述下产物或候选改变可能未改变前提摘要。方法别名也可能逃过重复识别。工具暂时不可用后恢复与数学搜索预算不足应是两种重试理由，当前统一规则可能迫使模型改参数或加预算。验证记录绑定直接引用，但不等于所有上游派生依赖都已验证和版本化。

**建议：** 使用稳定方法标识、规范化参数和实际依赖版本组成身份；描述保留给人和模型阅读。依据依赖关系使下游记录失效，并区分基础设施重试和计算续跑。先处理具体误判，不急于实现适用于所有数学约束的通用范围合并。

**后续验收：** 同义描述不重复计算；相关产物变化触发重新判断；无关展示文字变化不使算术结果失效；修复依赖后允许有上限、可解释的重试。

### R08 · P2：镜像固定不完整，已有容器不会自动采用新环境

**证据：静态确认；当前运行容器是否陈旧未检查。** [docker_runtime.py](../echo_agent/server/docker_runtime.py) 第 74 行起只检查容器是否存在/运行，没有比较镜像 ID、挂载集合或能力版本。[Dockerfile](../container/Dockerfile) 使用 `kalilinux/kali-rolling:latest` 与未锁定的系统包；[crypto-requirements.txt](../container/crypto-requirements.txt) 锁定了密码 Python 包，但不等于整个环境完全可重复构建。

**影响：** 更新镜像标签不会替换已创建容器；已有 bind mount 的内容更新可以可见，新增挂载和镜像内安装项则需要重建容器。宿主机 dispatcher/server 代码的变更还要求运行进程加载新代码，不能笼统归因于“没挂载”。验证记录目前以 `crypto-verify-v1` 标识方法，没有完整记录实际库版本、后端和镜像摘要。

**建议：** 在任务运行证据中记录服务代码版本、镜像 ID、工具自检结果和关键挂载；发现不匹配时提示明确的迁移/重建步骤，先保留产物再操作。稳定镜像可固定 digest 并有计划升级；不要求用户在宿主机额外装一套大型数学环境。共享 Dockerfile 的变化仍需考虑原渗透环境兼容性。

**后续验收：** 分别核对新建、旧容器、重启服务三种情形。本轮没有操作现有容器，也不能据此断言用户当前容器已经过期。

**同日后续部署记录：** 用户另行授权后已重新构建 `echo-agent-worker:crypto-s03` 并启动加载当前代码的宿主机服务；临时只读容器内新指引与本地文件哈希一致，见 [环境更新记录](crypto-runtime-update-20261022.md)。旧项目容器未重建，仍绑定各自原镜像。此次人工更新没有实现自动版本识别或迁移，不代表 R08 的机制建议已全部完成。

### R09 · P2：完成门槛局限于调度器，平台回执只是阻断开关

**证据：静态确认。** [app.py](../echo_agent/server/app.py) 第 277 行的 PUT 与第 310 行的状态 PATCH 没有统一调用密码完成验证；[models.py](../echo_agent/models.py) 的 `complete/transition_to` 只处理状态转换。[core.py](../echo_agent/dispatcher/core.py) 对 `require_platform_acceptance=true` 直接拒绝完成，没有受信回执入口；规划上下文也未直接给出该开关。

**影响：** “completed 必然代表独立验证通过”不是全系统不变量。若手动/API 完成是产品允许的行为，需要区分人工标记与机器验证。要求平台回执的任务目前可以被保守阻止，但不能完成受信回执闭环，也不应通过关闭该开关掩盖未验收状态。

**建议：** 明确完成语义并在公共服务层执行；若保留人工结束，记录来源与验证状态。平台支持可以暂缓，但界面应区分本地验证通过、待平台确认、平台已接受，并向 reason 提供实际完成要求。不得让模型自行填一条“平台接受”记录代替回执。

**后续验收：** 各入口的相同状态含义一致；缺少回执时清楚显示待确认，不循环声称已完成。此项是状态语义问题，不是对未授权攻击的推断。

### R10 · P2：验收证据尚不足以支持“稳定、完整兼容”的结论

**证据：静态阅读历史记录与测试源码。** [S09 实施记录](crypto-s09-implementation.md) 记录了 92 项检查中 91 通过、1 跳过，以及真实 Docker AES 正反例。本文保留这些历史结果，不重新执行，也不改写为本轮观察。S09 调度测试使用自行实现 `verify_crypto_candidate` 的 `Client` 和固定 `Reasoner`；HTTP 服务测试不等于网页后台链路测试。多根测试还主动期待 `pass`，缺少目标语义断言。

**影响：** 这些结果证明若干数据流、校验算法和容器路径可用，尚不能证明真实模型按契约稳定产出、完整题型覆盖、两类生产入口一致或原渗透功能完全无回归。进度文档原来的 `8/10` 与已记录 S09 的状态也不一致；改成 `9/10` 仍不能代表验收通过率。

**建议：** 将阶段交付、固定样例检查、真实模型端到端、原能力兼容分别记录。不要仅扩大测试数量；先增加能推翻错误完成结论的反例，再做受控真实模型试跑。

**后续验收：** 使用第 4 节矩阵，保留命令、版本、输入哈希、结果与未覆盖项。与 S01 既有失败逐项对照，不能将旧失败冒充新回归，也不能因为局部测试通过就宣称全部兼容。

## 5. 避免削弱原渗透能力的约束

修补应尽量限制在 `task_type=crypto` 的规则和公共服务的一致性上，保留现有 general 任务的 URL 入口、工具、提示词和 fact/intent 生命周期。密码验证状态不应直接重定义所有任务的 evidence；交互会话方案也不能全局取消进程清理。共享模型、API、存储、运行时和 Dockerfile 如有变化，需要针对对应旧行为复核。

本轮未运行兼容测试，因此只能判断这种隔离设计有利于兼容，不能据静态审阅保证原有渗透能力绝无减弱。后续先修补已确认缺口，再以已有 S01 基线和相关场景核实。
