# BUG-023/024 修复：outcome 契约与解析批隔离

日期：2026-10-22（Asia/Shanghai）。范围是 #44 `first_run` 暴露的两项问题。只修改工作区，不提交或推送 Git，不调用真实模型，不重跑原题，不重建镜像、不重启服务、不改数据库。

## 1. 问题

- **BUG-023**：密码提示词允许 `crypto.fact.claim_status=hypothesis`，但 `outcome` 只接受 `verified/refuted/error`，没有说明 hypothesis 该用什么值；模型写了 `inconclusive`，`_optional_worker_outcome()` 抛 `worker output outcome must be verified, refuted or error`。
- **BUG-024**：`parse_worker_result()` 对每个对象直接调用 `_worker_result_from_data()`，任一对象抛出 `ValueError` 就让整个函数失败。项目 #44 的 14 个对象中 13 条合法，因 1 条 `inconclusive` 全部丢失。

两项必须同批处理：只做隔离会把 hypothesis 当成最终结果；只做归一化仍可能被其他坏对象吞掉整批。

## 2. 改动

| 位置 | 处理 |
| --- | --- |
| `dispatcher/prompts.py::_crypto_contract_rules` | 明确 `outcome` 只取 `verified/refuted/error`，不得写 `inconclusive`/`hypothesis`；未验证的猜测不要单独输出，确需记录时用 `outcome=error` + `claim_status=hypothesis` |
| `container/AGENTS.md` | 同步同一规则（镜像需重建后生效） |
| `dispatcher/parsing.py::_optional_worker_outcome` | `inconclusive`、`hypothesis` 兼容归一化为 `error`；信任语义继续由 `claim_status` 承载 |
| `dispatcher/parsing.py::parse_worker_result` | 逐对象 `try/except ValueError`；坏对象记入 `WorkerResult.rejected`（对象序号 + 原因）后跳过；全部对象都坏时才抛汇总错误 |
| `dispatcher/parsing.py::parse_worker_result` | `claim_status=hypothesis` 的对象降级为 prior observation，不参与「最后一条结果」竞争；只有全部对象都是 hypothesis 时才保留最后一条，用于保存待核实事实 |
| `dispatcher/parsing.py::substantive_worker_output` | 超时 salvage 路径同样逐对象容错 |
| `dispatcher/types.py` | `WorkerResult` 新增 `rejected: list[str]` |
| `dispatcher/agents.py::CodexWorker.execute_intent` | 被拒对象以 warning 日志输出（最多前 10 条） |
| `dispatcher/core.py::_apply_crypto_intent_result` | 写入 `crypto.executions[].rejected_output_objects`（最多 20 条），供下一轮 reason 与事后审计 |

## 3. 行为变化

- 一个坏对象不再改变整批语义：合法的观察照常落 fact，坏对象只留下可追踪的警告。
- `outcome=inconclusive` 的 hypothesis 对象会进入待核实区（`FactKind.ERROR` + `claim_status=hypothesis`），不会进入 evidence，也不会放宽完成门槛。
- 模型把 hypothesis 放在最后时，`last wins` 会选最后一条**非 hypothesis** 观察作为结果；13 条合法观察 + 尾部假设的场景可以正常完成 intent。
- 如果一批里只有 hypothesis，最后一条仍作为结果记录为待核实事实，intent 记为失败，不静默丢输出。
- 不新增 outcome 枚举，不改 `IntentOutcome`、状态机或完成判定。
